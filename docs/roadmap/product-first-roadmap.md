# КПNEWS — Product-First Roadmap

## 1. Главная цель

Цель проекта — не создание архитектуры, инфраструктуры или набора технических модулей сами по себе.

Цель проекта — **рабочий редакционный продукт**, который человек может открыть, увидеть, использовать и оценить по реальному выпуску новостей.

Пользовательский результат считается достигнутым только тогда, когда редактор может пройти путь:

```text
открыть КПNEWS
→ увидеть ленту новостей
→ открыть сюжет и источники
→ понять, какие факты подтверждены
→ выбрать или получить предложенный набор новостей
→ сформировать черновик выпуска
→ прочитать эфирный текст
→ вручную исправить и утвердить выпуск
```

Технический фундамент, зелёный CI, база данных, API и модели данных являются средствами достижения этой цели, но не заменяют продуктовый результат.

## 2. Принцип разработки

Каждый следующий этап обязан давать наблюдаемое улучшение пользовательского сценария.

Перед началом работы над новым компонентом задаётся вопрос:

> Что нового редактор сможет увидеть или сделать после завершения этого этапа?

Если ответ ограничивается формулировками «появился модуль», «создана таблица», «добавлена инфраструктура» или «подготовлен контракт», этап не считается самостоятельным продуктовым результатом.

Основной принцип сохраняется:

> AI предлагает и объясняет. Детерминированный код контролирует ограничения. Человек-редактор принимает окончательное решение.

## 3. Текущее состояние

После merge `radio-news/main@10322460f30ff6dafbc0edb54d9a56420e5f0105` проект имеет самостоятельное исполняемое ядро:

```text
Source
→ RawItem
→ NormalizedItem
→ Story
→ Claim
→ Manual Fact
→ VerificationResult
→ SQLite
```

Подтверждено:

- пакет устанавливается независимо от Horizon;
- fixture проходит полный pipeline;
- данные сохраняются и восстанавливаются после перезапуска;
- повтор идентичных данных не создаёт дублей;
- конфликт provenance блокируется;
- миграции, wheel и CI работают.

Однако это ещё не пользовательский продукт.

```text
Технический фундамент: готов
Исполняемое ядро: готово
Редакторский интерфейс: отсутствует
Реальная лента: отсутствует
Черновик выпуска: отсутствует
Пользовательский результат: ещё не достигнут
```

## 4. Первый продуктовый рубеж — Visible Editorial MVP

Ближайшая цель проекта:

> Редактор открывает локальное приложение и видит новости, сюжеты, источники и первый черновик выпуска.

Минимальный пользовательский сценарий:

```text
запуск одной командой
→ локальная страница в браузере
→ список сохранённых новостей
→ карточка сюжета
→ источник и provenance
→ Claim и Manual Fact
→ статус VerificationResult
→ ручной выбор нескольких сюжетов
→ кнопка «Сформировать выпуск»
→ простой черновик выпуска на экране
```

На этом рубеже допускаются:

- локальные fixtures или заранее сохранённые материалы вместо live RSS;
- ручное подтверждение фактов;
- ручной выбор сюжетов;
- детерминированный шаблон текста вместо полноценного AI Radio Writer;
- простой линейный список вместо Rundown Solver;
- минимальный локальный Web UI без дизайна production-уровня.

Не допускается выдавать технический CLI или JSON как пользовательский MVP.

## 5. Новый порядок ближайшей разработки

### Product Slice P1 — Read-only Editorial Feed

Пользователь видит:

- список Source и RawItem;
- заголовок, время и источник;
- состояние обработки;
- отсутствие дублей;
- понятное пустое состояние и ошибки.

Технический scope:

- read-only application service;
- локальный HTTP API;
- минимальный Web UI;
- список материалов из существующей SQLite;
- запуск одной командой.

Definition of Done:

```text
редактор запускает приложение
→ открывает браузер
→ видит сохранённую новость без работы с терминальным JSON
```

### Product Slice P2 — Story and Evidence View

Пользователь открывает материал и видит:

- Story;
- RawItem и NormalizedItem;
- Claim;
- Manual Fact;
- VerificationResult;
- source fingerprint;
- связи между сущностями.

Definition of Done:

```text
редактор может глазами проверить:
кто сообщил
что именно утверждается
какой факт принят
почему система показывает READY или NEEDS_REVIEW
```

### Product Slice P3 — Manual Editorial Selection

Пользователь может:

- отметить сюжет для выпуска;
- снять выбор;
- задать порядок;
- назначить роль `lead`, `body`, `reserve`;
- сохранить черновой Editorial Selection.

На этом этапе не требуется Chief News Editor.

Definition of Done:

```text
редактор вручную собирает список сюжетов будущего выпуска
и после перезапуска видит тот же сохранённый выбор
```

### Product Slice P4 — Deterministic Draft Edition

Система создаёт первый видимый черновик выпуска:

- заголовки выбранных сюжетов;
- короткий текст из утверждённых Facts;
- источник и обязательная атрибуция;
- порядок новостей;
- приблизительный хронометраж;
- ручное редактирование текста;
- статус `DRAFT`.

На этом этапе текст может строиться детерминированным шаблоном без LLM.

Definition of Done:

```text
редактор нажимает «Сформировать выпуск»
→ получает на экране связный черновик
→ правит его
→ сохраняет
```

### Product Slice P5 — First Editorial Acceptance

Один реальный редактор оценивает выпуск по критериям:

- уместность выбранных сюжетов;
- ясность текста;
- происхождение фактов;
- удобство интерфейса;
- время подготовки;
- объём ручной доработки.

Definition of Done:

```text
подготовлен один выпуск
редактор понял, что сделал продукт
зафиксированы замечания
принято решение о следующем приоритете
```

## 6. Что сознательно откладывается до Visible Editorial MVP

До прохождения Product Slice P5 не расширять проект следующими крупными подсистемами, если они не блокируют пользовательский сценарий:

- полный live RSS ingress;
- перенос webhook SSRF transport;
- множество collectors;
- сложный Story clustering через embeddings;
- все Editorial Personas;
- Chief News Editor;
- полноценный AI Radio Writer;
- Rundown constraint solver;
- Breaking News Controller;
- Pronunciation Engine;
- production export;
- newsroom integration;
- сложный дизайн Web UI;
- микросервисы;
- масштабирование инфраструктуры.

Эти части остаются в основном архитектурном roadmap, но не должны отодвигать первый видимый продукт.

## 7. Product Gate

Новый обязательный gate для каждой крупной фазы:

```text
VISIBLE VALUE: что увидел пользователь
USER ACTION: что он смог сделать
EVIDENCE: как это проверено
EDITORIAL FEEDBACK: что сказал редактор
NEXT BLOCKER: что мешает следующему полезному действию
```

Фаза не закрывается только по признакам:

```text
tests passed
CI green
schema created
module implemented
API available
```

Они обязательны для качества, но недостаточны для продуктовой приёмки.

## 8. Два типа готовности

В отчётах всегда разделяются:

### Engineering Ready

- код работает;
- тесты проходят;
- данные целостны;
- CI зелёный;
- контракт выполнен.

### Product Ready

- пользователь видит результат;
- основной сценарий выполняется без инженерных знаний;
- результат можно оценить редакторскими критериями;
- интерфейс показывает ошибки и происхождение данных;
- есть сохранённый полезный артефакт: подборка, текст или выпуск.

Запрещено называть `Product Ready` результат, который можно увидеть только через pytest, SQLite shell, JSON CLI или GitHub Actions.

## 9. Обновлённая ближайшая последовательность

```text
Исполняемое ядро — COMPLETE
↓
P1 Read-only Editorial Feed
↓
P2 Story and Evidence View
↓
P3 Manual Editorial Selection
↓
P4 Deterministic Draft Edition
↓
P5 First Editorial Acceptance
↓
только затем:
live ingress / scoring / personas / Chief Editor / AI Writer / Rundown
```

## 10. Главный критерий проекта

Проект существует не ради правильной архитектуры.

Архитектура нужна, чтобы продукт не обманывал редактора, не терял происхождение данных и не разваливался при развитии.

Но итоговая цель остаётся простой:

> КПNEWS должен помогать редактору быстрее и качественнее собрать реальный радиовыпуск, а результат этой помощи должен быть виден на экране.
